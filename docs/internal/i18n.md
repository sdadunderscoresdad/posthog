# Internationalization

The frontend renders every message through i18next.
This doc says what the framework gives you, how to add a string, and which shapes are not allowed.

## Why the messages live in the source, not in a translator pass over the DOM

A translation layer that rewrites rendered text nodes cannot translate real product copy.
It sees one flat string with no identity, no variable boundaries, and no structure, so it cannot
handle a sentence built by concatenation, a duration produced at runtime, or a count that changes
the wording in a way English does not.

PostHog has all three shapes today, and they are the reason this framework exists:

- `humanFriendlyDuration` builds `1d 10hrs 9mins 8s` from four separate pieces.
- `humanFriendlyCurrency` hardcodes `en-US` and `$`.
- `compactNumber` hardcodes the `K`/`M`/`B` suffixes.

So the unit of translation is a **message with named placeholders, declared where the data is still
available**, and everything that is not a message is formatted by `Intl` for the active language.

## The model

English is the source language, and its text sits at the call site rather than in a catalog. That
means no English catalog is shipped or loaded, a missing translation degrades to correct English
rather than to a key, and a reviewer reads the copy in the component.

```tsx
const { t } = useTranslation()

// One message, one key, English inline. The catalog holds only the translations.
t('dashboards.deleteConfirm', { defaultValue: 'Delete {{name}}?', name: dashboard.name })
```

```tsx
import { Trans } from 'react-i18next'

const count = 3

// A sentence that contains markup is still one message. Never split it to insert a component.
<Trans i18nKey="insights.eventLimit" count={count}>
    Your project has used {{ count }} of its events. <strong>Upgrade</strong> to keep them.
</Trans>
```

Keys are stable and namespaced (`<surface>.<thing>`). The English text can change without orphaning
a translation, because the key is what identifies the message.

Inside `<Trans>` children, the placeholder keeps its `{{ count }}` braces and the name has to be a
variable in scope. `Trans` reads that object as the interpolation, so the English default and the
catalog agree on where the value goes. Writing `{count}` renders nothing, because `Trans` consumes
the expression as a placeholder and then finds no value bound to it.

Markup goes in the children as the real element. `Trans` records each element by its position, so the
catalog carries a numbered tag such as `<1>` and the runtime maps it back to that element. Name a
slot after an HTML void element and React rejects it the moment the English text renders: `<link>` is
the HTML `link` tag, which cannot have children. Write the component itself.

## Rules

1. **Never build a sentence from pieces.** `'Delete ' + name + '?'` cannot be reordered, inflected,
   or translated. Make it one message with `{{name}}`.
2. **Never branch on a count to choose wording.** Pass `count` and let the plural rules of each
   language decide. Russian, Arabic, and Polish have plural forms English does not, and the
   framework asks for all of them.
3. **Format values with `useFormatters()`, not with string concatenation.** Numbers, currency,
   percentages, dates, times, durations, and lists all render differently per language.
4. **Pass data, not markup.** Rich text goes through `Trans`, so the translated sentence can move
   the link or the emphasis anywhere.

An empty string in a catalog is not a translation. The extractor writes one for every message a
language has not done yet, and i18next is configured to treat it as missing so those messages fall
back to the English at the call site. Without that setting an untranslated language renders blank
labels.

## The pieces

| Concern                                                  | File                                                    |
| -------------------------------------------------------- | ------------------------------------------------------- |
| Which languages exist, and their direction and script    | `frontend/src/lib/i18n/supportedLocales.ts`             |
| Which namespaces exist                                   | `frontend/src/lib/i18n/namespaces.ts`                   |
| Tag matching and start-up language choice                | `frontend/src/lib/i18n/localeResolution.ts`             |
| Remembering the choice on this device                    | `frontend/src/lib/i18n/localePersistence.ts`            |
| The i18next instance and catalog loading                 | `frontend/src/lib/i18n/i18n.ts`                         |
| React binding, `<html lang>` and `<html dir>`            | `frontend/src/lib/i18n/I18nProvider.tsx`                |
| Locale-aware number, date, duration, and list formatting | `frontend/src/lib/i18n/formatters.ts`                   |
| Catalogs                                                 | `frontend/src/lib/i18n/locales/<code>/<namespace>.json` |
| The generated import map                                 | `frontend/src/lib/i18n/catalogLoaders.ts`               |

`I18nProvider` must sit above everything that renders text, inside a `Suspense` boundary. It waits
for the active language's catalogs before rendering children, so no component ever renders a raw
key. The source language has no catalog, so English never waits.

`catalogLoaders.ts` is generated. Each catalog is a separate `import()`, which is what makes a
language choice cost one chunk instead of shipping every language.

## Adding a string

1. Pick a key in the namespace that owns the surface.
2. Write the English text at the call site, through `t` or `Trans`.
3. Run `pnpm --filter=@posthog/frontend i18n:extract` to refresh the source catalog, then
   `pnpm --filter=@posthog/frontend i18n:build`.

## Adding a language

1. Add an entry to `SUPPORTED_LOCALES`.
2. Add `frontend/src/lib/i18n/locales/<code>/` with a file for every name in `NAMESPACES`.
3. Run `pnpm --filter=@posthog/frontend i18n:build`.

The build script fails when the registry and the directories disagree, when a translation invents a
key the source does not have, or when a translation drops a placeholder.

## Adding a namespace

Add the name to `NAMESPACES`, then create `<namespace>.json` for every supported language. An
untranslated namespace can start as `{}`, which renders the English at each call site.

## Commands

```sh
pnpm --filter=@posthog/frontend i18n:extract   # write the source catalog from the call sites
pnpm --filter=@posthog/frontend i18n:build     # regenerate the import map
pnpm --filter=@posthog/frontend i18n:check     # verify catalogs and the import map, without writing
```

## Not built yet

- **Type-checked keys.** A mistyped key renders its English text and silently never gets
  translated. `i18next-cli types` generates the declaration that makes a wrong key a type error;
  it needs a non-empty source catalog to be worth turning on.
- **The language picker.** Users cannot change language from the UI yet.
- **Account-level preference.** `resolveLocale` already accepts `userPreference` and gives it
  priority, but nothing reads a saved preference from the API yet.
- **Lint coverage for concatenation.** The rules above are conventions today.
